# 共通ルール

<!-- 見本。~/.claude/CLAUDE.md に置くと、全プロジェクトで読み込まれる。自分の進め方に合わせて書き換えて使う。 -->

全プロジェクトに共通する進め方。プロジェクトに独自のルール(CLAUDE.md、AGENTS.md)がある場合は、そちらを優先する。

## 進め方

- 新しい作業は、着手する前に目的・要件・制約をヒアリングする。不明点は推測せずに質問する
- 作業計画を示し、承認を得てから実行する
- 利用者に質問するときは、利用者が経緯を覚えていない前提で、出典の原文と文脈、なぜ聞くのか、答えで何が変わるのかを先に見せる。件名や番号だけで聞かない。聞いていないことを、答えをもらったことにして片づけない
- 誤字の修正や単純な質問のような軽い依頼では、この手順を省く

## 記録

- 次回以降も必要になる情報(URL、環境、関係者、決定事項、未決事項)は、指示がなくてもプロジェクト内に記録する
- 保存先と形式は自分で決め、利用者に尋ねない。記録したら場所を一言で報告する
- 作業の区切りで `TODO.md` の「現在地」と残タスクを更新する
- `/00-kickoff` で始めたプロジェクトでは、利用者が動くこと・待つことを、`docs/00_前提/タスクボード.md` のカードにする。相手に何かを送ったとき、相手から返事が来たとき、利用者がやること・決めることが増えたとき・片づいたときに、確認を取らずにカードを足す・移す・消す。書き換えたら一言で報告する。書き方は `~/.claude/skills/00-board/format.md` にあり、書き換える前に読む
- 利用者に読んで確かめてもらう報告(調査結果、比較、計画の案など)は、外部の読み込みのない 1 つの HTML ファイルに書く。`<title>` の先頭に、プロジェクトのフォルダ名を入れる(例:`my-project 計画の案`)。どのプロジェクトのタブかを、利用者が見分けるため。HTML に入れるリンクは、新しいタブで開くようにする(`target="_blank" rel="noopener"`)。プロジェクトに残す記録(`TODO.md`、決定事項、README、ルール)と、成果物が Markdown のものは Markdown のまま書く
- ファイルの確認を利用者に依頼するときは、パスを伝えるだけでなく、そのファイルを開いて見せる(macOS では `open`)。同じファイルを開き直すときは、古いタブを残さない
- あとに残さない報告の HTML は、一時的な置き場(スクラッチパッド)に書く。利用者が報告に返事をして次の話題に移ったら、自分が開いたタブを閉じ、一時的な置き場のファイルを消す。利用者が報告を読むのは返事をするときだけで、残しておくとタブとファイルがたまるため

## 置き場所

- 標準構成と命名規則は `~/.claude/skills/00-kickoff/structure.md` にある。ファイルを新しく作るときと、置き場所に迷ったときに読む
- 標準にない種類のファイルやフォルダが必要になったら、作る前に「このプロジェクトだけか、標準に加えるか」を質問する
- 標準構成でない既存プロジェクトでは、その構成に合わせる。頼まれない限り作り替えない

## 改善

指摘を受けたとき、または自分で問題に気づいたときは、次の順で対処する。

1. まずその場で直す
2. 原因を一言で特定する(ルールがなかった / 曖昧だった / あったが守らなかった)
3. 「今後は」と言われた場合と、同じ指摘が 2 回目の場合にルールにする。そのプロジェクトだけの話はプロジェクトの `CLAUDE.md` に書いて報告する。作業の種類に共通する話は `99-rules-*` skill に、全作業に共通する話はこのファイルに書く。どちらも「共通のものを直すとき」に従う。機械的に判定できる決まりは hook を提案する
4. ルールは追記より既存の行の書き換えを優先し、重複や古いものは統合・削除する

プロジェクトの `CLAUDE.md` にある次回点検日を過ぎていたら、`/00-checkup` の実行を提案する。

## 共通のものを直すとき

skill(`~/.claude/skills/` の下)とこのファイルは、全プロジェクトで共通に使う。それぞれ管理しているプロジェクトがあり、そのプロジェクトのセッションだけが直す。

- skill を管理しているプロジェクトは、`~/.claude/skills/<名前>` のリンク先で分かる。このファイルは、共通ルールを管理するプロジェクト(自分で決める)が管理する
- 管理しているプロジェクトのセッションでは、変更案を示し、了承を得てから直す
- ほかのプロジェクトのセッションでは、直接書き換えない。管理しているプロジェクトに依頼を書く(書き方は「ほかのプロジェクトへの依頼」)
- リンクでない skill(管理しているプロジェクトがない)は、直す前に利用者に確かめる

## ほかのプロジェクトへの依頼

- ほかのプロジェクトのファイルは、直接書き換えない。伝えたいこと(直してほしいこと、点検の所見など)は、相手のプロジェクトの `docs/90_依頼/` に `YYYY-MM-DD_<件名>.md` で依頼を書き、書いたことを利用者に一言伝える。節は「起きたこと」「直してほしいこと(案)」「確かめてほしいこと」の 3 つ
- 依頼を書いてよい相手は、`~/.claude/kickoff-projects.txt` にあるプロジェクトだけ。共通のものを管理しているプロジェクトあての依頼は、確認なしで書いてよい。それ以外のプロジェクトあては、利用者に頼まれたときだけ書く。相手に `docs/90_依頼/` がなければ、作ってよい
- 未対応の依頼(`docs/90_依頼/` の直下にあるもの)があれば、セッションの最初に伝える。対応したら、依頼の末尾に「対応」の節を足して何をしたかを書き、`docs/90_依頼/対応済み/` に移す
- 開いたままのセッションには、依頼が届いたことが伝わらない(知らせるのはセッションの最初だけ)。急ぐときは、利用者から相手のセッションに一言伝えてもらう

## 作業範囲

- 読み書きは作業フォルダの配下に限る。外に出る必要があるときは、先に確認する。ただし、「ほかのプロジェクトへの依頼」に従って依頼を書くときは、そこにある条件のとおりでよい
