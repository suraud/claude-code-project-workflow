# 共通ルール

<!-- 見本。~/.claude/CLAUDE.md に置くと、全プロジェクトで読み込まれる。自分の進め方に合わせて書き換えて使う。 -->

全プロジェクトに共通する進め方。プロジェクトに独自のルール(CLAUDE.md、AGENTS.md)がある場合は、そちらを優先する。

## 進め方

- 新しい作業は、着手する前に目的・要件・制約をヒアリングする。不明点は推測せずに質問する
- 作業計画を示し、承認を得てから実行する
- 誤字の修正や単純な質問のような軽い依頼では、この手順を省く

## 記録

- 次回以降も必要になる情報(URL、環境、関係者、決定事項、未決事項)は、指示がなくてもプロジェクト内に記録する
- 保存先と形式は自分で決め、利用者に尋ねない。記録したら場所を一言で報告する
- 作業の区切りで `TODO.md` の「現在地」と残タスクを更新する
- ファイルの確認を利用者に依頼するときは、パスを伝えるだけでなく、そのファイルを開いて見せる(macOS では `open`)

## 置き場所

- 標準構成と命名規則は `~/.claude/skills/00-kickoff/structure.md` にある。ファイルを新しく作るときと、置き場所に迷ったときに読む
- 標準にない種類のファイルやフォルダが必要になったら、作る前に「このプロジェクトだけか、標準に加えるか」を質問する
- 標準構成でない既存プロジェクトでは、その構成に合わせる。頼まれない限り作り替えない

## 改善

指摘を受けたとき、または自分で問題に気づいたときは、次の順で対処する。

1. まずその場で直す
2. 原因を一言で特定する(ルールがなかった / 曖昧だった / あったが守らなかった)
3. 「今後は」と言われた場合と、同じ指摘が 2 回目の場合にルールにする。そのプロジェクトだけの話はプロジェクトの `CLAUDE.md` に書いて報告する。作業の種類に共通する話は `99-rules-*` skill に、全作業に共通する話はこのファイルに書く。どちらも「共通のものを直すとき」に従う。機械的に判定できる決まりは hook を提案する
4. ルールは追記より既存の行の書き換えを優先し、重複や古いものは統合・削除する

プロジェクトの `CLAUDE.md` にある次回点検日を過ぎていたら、`/00-checkup` の実行を提案する。

## 共通のものを直すとき

skill(`~/.claude/skills/` の下)とこのファイルは、全プロジェクトで共通に使う。それぞれ管理しているプロジェクトがあり、そのプロジェクトのセッションだけが直す。

- skill を管理しているプロジェクトは、`~/.claude/skills/<名前>` のリンク先で分かる。このファイルは、共通ルールを管理するプロジェクト(自分で決める)が管理する
- 管理しているプロジェクトのセッションでは、変更案を示し、了承を得てから直す
- ほかのプロジェクトのセッションでは、直接書き換えない。管理しているプロジェクトの `docs/90_依頼/` に `YYYY-MM-DD_<件名>.md` で依頼を書き、書いたことを利用者に一言伝える。節は「起きたこと」「直してほしいこと(案)」「確かめてほしいこと」の 3 つ
- 管理しているプロジェクトのセッションは、未対応の依頼(`docs/90_依頼/` の直下にあるもの)があれば、セッションの最初に伝える。対応したら、依頼の末尾に「対応」の節を足して何をしたかを書き、`docs/90_依頼/対応済み/` に移す
- リンクでない skill(管理しているプロジェクトがない)は、直す前に利用者に確かめる

## 作業範囲

- 読み書きは作業フォルダの配下に限る。外に出る必要があるときは、先に確認する。ただし、「共通のものを直すとき」の依頼を書くときは、確認しなくてよい
