# プロジェクトの定期点検

プロジェクトが標準構成からずれていないか、用意したファイルが実際に使われているかを確かめ、直すべき点を直す。ずれの原因が標準の側にある場合は、標準を直す。

基準は `~/.claude/skills/00-kickoff/structure.md`。最初に読む。

指示ファイルの中身(CLAUDE.md や skill の古い記述、矛盾)は、この skill では調べない。公式の `/doctor prompt-audit` と `/skill-doctor` が担当するので、使える場合は最後に実行を案内する。

## 手順

### 1. Check:現状を調べる(読み取りのみ)

この段階では何も変更しない。次の 4 つの観点で調べる。

**構成**
- 標準にないフォルダやファイル、プロジェクト直下に散らかったファイル
- 残骸(`~$` で始まる Office のロックファイル、`.DS_Store`、`hoge` や `test` のような試作ファイル)
- 版をファイル名で表しているもの(`OLD_`、`_v2`、`bk`、`.bak`、`_下書き`)
- 生成物(xlsx、pdf、html)だけがあり、正本の md が見当たらないもの

**使われ方**
- `{{ }}` が残っているなど、雛形のままのファイル
- 30 日以上更新されていない `TODO.md` と `docs/00_前提/`(git の履歴か更新日時で確かめる)
- 空のフォルダ
- `CLAUDE.md` の参照先に書かれているのに存在しないファイル
- `確認事項.md` に長く残っている未解決項目

**ルール**
- プロジェクトの `CLAUDE.md` の行数(目安は 30 行以内)と、重複・矛盾する固有ルール
- 前回の点検以降に追加された固有ルールのうち、他のプロジェクトにも当てはまりそうなもの

**安全**
- 秘密情報らしきファイル(`credentials`、`token`、`secret`、`.env`、`.pem`、`.key`)が git の管理対象になっていないか。中身は開かず、ファイル名と管理状態だけを見る
- コミットされていない変更の量

### 2. 報告する

所見を次の 3 つに分けて示す。それぞれ、何が、どこにあり、どう直すかを 1 行ずつ書く。所見がない区分は「なし」と書く。

1. **プロジェクト側を直す**:標準に合わせて移動・改名・削除するもの
2. **標準を直す**:このプロジェクトのやり方のほうが実態に合っていて、`structure.md` と雛形を変えたほうがよいもの
3. **例外として残す**:理由があって標準と違うもの

削除と移動は元に戻しにくいので、対象のファイルを具体的に挙げる。

### 3. Act:承認されたものだけ直す

利用者が承認した項目だけを実施する。

- 移動や削除の前に、対象が git で追跡されているかを確かめる。追跡されていないファイルを消すと戻せないので、削除ではなく `archive/` への移動を優先する
- 標準を直す場合は、`structure.md` と `~/.claude/skills/00-kickoff/templates/` を一緒に更新する
- 例外として残すものは、`決定事項.md` に理由を 1 行書く

### 4. Plan:記録して次回を決める

- `docs/00_前提/決定事項.md` に、点検日・直したこと・見送ったことを 2〜3 行で残す
- プロジェクトの `CLAUDE.md` の次回点検日を 30 日後に更新する
- `/doctor prompt-audit` と `/skill-doctor` が使える場合は、実行を案内する

## 引数 all:横断点検

`all` が指定されたら、親フォルダ直下の各プロジェクトを読み取りのみで比較する。個々のプロジェクトは直さない。親フォルダは `all` に続く引数で受け取る。省略されたら、現在のフォルダの親を案として示し、確かめてから進める。

- 各プロジェクトについて、標準構成かどうか、標準からのずれ、最後に更新された時期を一覧にする
- 複数のプロジェクトに共通するずれを抜き出す。共通するずれは、標準が実態に合っていない兆候なので、標準の見直し案として示す
- 標準の変更は、承認を得てから `structure.md` と雛形に反映する

## 標準構成でないプロジェクト

`/00-kickoff` で作られていない既存プロジェクトでは、報告だけ行う。そのプロジェクトには独自の構成とルールがあるので、頼まれない限り作り替えない。
