# プロジェクトの標準構成

新規プロジェクトの作成(`/00-kickoff`)、定期点検(`/00-checkup`)、日々のファイル配置の基準。どのプロジェクトでも同じ場所に同じ種類のものがある状態を保つために、ここを唯一の正本にする。

変更するときは利用者の了承を得て、このファイルと `templates/` を一緒に直す。

## 構成

```
<プロジェクト>/
  README.md          人が読む入口。何のプロジェクトか、できること、使い方、状況
  CLAUDE.md          Claude 向けの入口。概要、参照先の一覧、固有ルール、次回点検日(20 行前後)
  TODO.md            現在地と残タスク
  .gitignore
  docs/              成果物。正本は md
    00_前提/         プロジェクトの参照情報
      概要.md        目的・ゴール・スコープ・成果物
      参照情報.md    URL・リポジトリ・環境・関係者
      決定事項.md    決定と理由、点検の記録
      確認事項.md    未決事項・質問
    10_〜 80_        成果物の種類ごとのフォルダ
    90_              保留・参考・議事など本筋でないもの
    images/          文書から参照する図や画像(必要になったら)
  references/        受領資料・外部からのコピー
  scripts/           生成・変換・同期スクリプト
  archive/           旧版
  public/            公開する成果物。独立した git リポジトリ(公開する場合だけ)
```

## 作る時期

- **最初から作る**:`README.md`、`CLAUDE.md`、`TODO.md`、`.gitignore`、`docs/00_前提/` の 4 ファイル
- **必要になったら作る**:`docs/10_〜`、`docs/images/`、`references/`、`scripts/`、`archive/`、`public/`。名前は上の構成に固定する

空の器を先に並べると、使われないまま残って紛らわしくなる。中身ができた時点で作る。

## 成果物を公開する場合(public/)

作ったもの(ツール、スキル、スクリプトなど)を GitHub などで公開する場合は、公開するものを `public/` に分ける。プロジェクトのフォルダには、作ったものと、作る過程の管理(`CLAUDE.md`、`TODO.md`、`docs/00_前提/`)が混ざる。後者には関係者の名前や経緯が入り、使う人には不要なため。

- `public/` の中で `git init` し、独立したリポジトリにする。外側の `.gitignore` に `public/` を加える。外側は管理用で、公開しない
- `public/` に置くもの:`README.md`、`LICENSE`、作ったもの本体、使う人向けの手順。`README.md` はプロジェクトの直下ではなく、ここに置く
- `public/` に書かないもの:個人名、社内や顧客の情報、作業の経緯、調査の生のメモ。経緯は外側の `決定事項.md` に書く
- コミットの前に、作者欄(`git config user.name`、`user.email`)を `public/` の中でも確かめる。個人の GitHub アカウントに置く場合は、noreply アドレスを使う(決め方は `SKILL.md` の初回コミットの手順にある)
- リモートへ送る前に、個人名、パス、秘密情報が含まれていないかを検索して確かめる

## README.md の書き方

`README.md` は人が読むためのもの。GitHub や GitLab でリポジトリを開いた人が、最初の画面で「何ができて、どう使うか」をつかめるように書く。

- 端的に書く。1 画面から 2 画面に収める。経緯や決定の理由は書かず、`docs/00_前提/` へ案内する
- 「できること」は利用者の目線で書く。内部の作りや作業の履歴を並べない
- 機能や使い方が変わったら、作業の区切りで書き直す。`TODO.md` の「現在地」と一緒に見直す
- `CLAUDE.md` と内容を重ねない。`CLAUDE.md` は Claude への指示、`README.md` は人への案内

## 置き場所の決め方

| 置くもの | 場所 |
|---|---|
| 成果物(設計書、手順書、報告、資料の正本) | `docs/<番号>_<種類>/` |
| 成果物から生成した xlsx・pdf・html・pptx | 正本と同じフォルダ |
| 文書に載せる図や画像 | `docs/images/`(公開する場合は `public/docs/images/`)。スクリプトで作る図は、スクリプトを `scripts/` に置く |
| 相手から受け取った資料、共有ドライブや課題管理のコピー | `references/` |
| URL、リポジトリ、環境、関係者 | `docs/00_前提/参照情報.md` |
| 決まったことと理由 | `docs/00_前提/決定事項.md` |
| まだ決まっていないこと、相手への質問 | `docs/00_前提/確認事項.md` |
| いまの状況と残タスク | `TODO.md` |
| 人に向けた案内(何ができるか、使い方) | `README.md`(公開する場合は `public/README.md`) |
| 公開する成果物 | `public/` |
| そのプロジェクトだけの作業ルール | `CLAUDE.md` の固有ルール |
| 置き換えた旧版 | `archive/` |

## 命名規則

- `docs/` 直下のフォルダは 10 刻みの番号を付ける(`10_現状分析`、`20_設計`)。あとから間に差し込めるようにするため
- 旧版は `archive/` に移す。`OLD_`、`_v2`、`bk`、`.bak`、`_下書き` のようにファイル名で版を表さない。履歴は git に残る
- xlsx・pdf・html などは md から生成し、生成物を直接編集しない。直接編集すると正本とずれ、再生成で消える
- `references/` の中身は編集しない。受領時の状態を保つため

## 作らないもの

`memo/`、`.agent/`、`.spec/`、AGENTS.md、GEMINI.md、PLAN.md、SPEC.md、HANDOFF.md、MEMORY.md。

引き継ぎは `TODO.md` の「現在地」欄が担う。やりたいことと要件は `概要.md` にまとめる。

## 標準にないものが必要になったら

標準にない種類のファイルやフォルダが必要になったら、作る前に利用者に質問する。選択肢は 2 つ。

- **このプロジェクトだけ**:作成し、`決定事項.md` に例外として 1 行残す
- **標準に加える**:このファイルと `templates/` を更新してから作成する

## 標準構成でないプロジェクト

この構成になっていない既存プロジェクトでは、そのプロジェクトの構成と独自ルールに合わせる。頼まれない限り作り替えない。
