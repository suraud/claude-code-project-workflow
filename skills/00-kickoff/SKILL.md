# 新規プロジェクトの開始

現在のフォルダを、標準構成のプロジェクトとして立ち上げる。利用者が用意するものはない。やりたいことを聞き取り、その内容を書き込んだ状態でファイルを作る。

標準構成の正本は [structure.md](structure.md)、雛形は `templates/` にある。作業の前に `structure.md` を読む。

## 手順

### 1. 既存の状態を確認する

現在のフォルダの中身を一覧し、標準構成のファイルやフォルダがすでにあるかを調べる。

- **すでにあるファイルは上書きしない。** 足りないものだけを作る。何度実行しても同じ結果になるようにするため
- 中身のあるフォルダ(既存の成果物がある、別のルールファイルがある)の場合は、そのまま進めず、標準構成に寄せるかどうかを先に尋ねる

### 2. ヒアリングする

引数があれば、それを「やりたいこと」として読む。ファイルのパスならその内容を読む。引数がなければ、やりたいことを自由に話してもらう。

次の 4 点が埋まるまで質問する。話の中ですでに出たことや推測できることは聞き直さず、案として示して確認する。質問は一度に 3 つまでにする(一度に答えやすい量に抑えるための目安)。

- 目的とゴール(何ができたら完了か)
- 成果物の種類(設計書、手順書、IaC、資料など)
- 関係者と期限
- 関連する URL(課題管理、リポジトリ、共有ドライブ)

あわせて、作ったものを GitHub などで公開する予定があるかを尋ねる。ある場合は、`structure.md` の「成果物を公開する場合」に従い、`public/` を独立したリポジトリとして作り、`README.md` はその中に置く。わからない場合は作らず、公開が決まった時点で分ける。

わからない項目は空欄にせず、`確認事項.md` に未決として載せる。

### 3. 構成を提示して承認を得る

作成するファイルの一覧と、成果物の種類から考えた `docs/10_〜` のフォルダ案を見せる。`docs/10_〜` は案を示すだけにとどめ、実際に中身ができたときに作る。承認を得てから次へ進む。

### 4. 作成する

`templates/` の各ファイルをもとに作る。`{{ }}` の箇所はヒアリング結果で埋め、雛形のまま残さない。

| 雛形 | 作成先 |
|---|---|
| `templates/README.md` | `README.md`(公開する場合は `templates/README-public.md` から `public/README.md`) |
| `templates/CLAUDE.md` | `CLAUDE.md` |
| `templates/TODO.md` | `TODO.md` |
| `templates/gitignore` | `.gitignore` |
| `templates/00_前提/*.md` | `docs/00_前提/` |

`references/`、`scripts/`、`archive/`、`docs/10_〜` はここでは作らない。空のフォルダは git に残らず、使われないまま紛らわしくなるため、中身ができたときに作る。`CLAUDE.md` の次回点検日には、作成日の 30 日後を入れる(点検は月に 1 回を目安にする)。

`README.md` は人が読むためのもの。書き方は `structure.md` の「README.md の書き方」に従う。開始時点では機能がまだないので、公開する場合の「特長」には目指す姿を、「動作環境」「インストール」「使い方」には「準備中」と書く。

### 5. git を初期化する

現在のフォルダがリポジトリの最上位でなければ、`git init` して初回コミットを作る。親フォルダがリポジトリであっても、このフォルダで初期化する。自動メモリは git リポジトリ単位で分かれるので、プロジェクトごとにリポジトリを持つと記憶が他のプロジェクトと混ざらない。

- **初回コミットの前に、コミットの作者欄を確かめる。** `git config user.name` と `git config user.email` を調べ、結果を利用者に示して、このプロジェクトで使う名前とメールアドレスを尋ねる。未設定のままコミットすると、git が OS のアカウントの氏名と「ユーザー名@ホスト名」を自動で記録し、リモートへ送ったときに外へ出るため
  - 設定済みの場合:その値を示し、このプロジェクトでもそれを使うかを確かめる
  - 未設定の場合、または別の値を使う場合:答えを `git config user.name`、`git config user.email` でこのリポジトリだけに設定する(`--global` は、利用者がこの端末全体への設定を望んだときだけ使う)
  - リポジトリの置き先を尋ね、答えに応じてアドレスを提案する。「このリポジトリは、個人の GitHub アカウントに置きますか、会社のリポジトリに置きますか、どこにも送りませんか」
    - 個人の GitHub アカウント:公開か非公開かを問わず、GitHub の noreply アドレス(`ID+ユーザー名@users.noreply.github.com`)を提案する。番号は `gh api users/<ユーザー名> --jq .id` で調べる。公開リポジトリのコミットのアドレスは誰でも読め、勧誘のメールの宛先に使われる。非公開でも、あとから公開に変えることがある
    - 会社のリポジトリ:会社のアドレスを提案する
    - どこにも送らない:いまの設定でよいかを確かめる。あとで送る可能性があるなら、上のどちらかに合わせる
  - 個人のアカウントに置く場合は、GitHub の Settings > Emails で「Keep my email addresses private」と「Block command line pushes that expose my email」が有効かを、利用者に確かめてもらう
  - 公開したあとでアドレスを変えると、履歴の書き換えと強制 push が要り、古いコミットは GitHub 上にしばらく残る。初回コミットの前に決める
- 不要と言われたら省く
- リモートへの push は、URL を受け取り、実行前に確認を取ってから行う
- `public/` を作った場合は、`structure.md` の「成果物を公開する場合」に従い、`public/.git/hooks/pre-push` を置く。`~/.claude/public-ng-words.txt` がなければ、止める語(利用者の氏名、メールアドレス、会社名など)を尋ねて作る

### 6. 一覧に登録する

`~/.claude/kickoff-projects.txt` に、このフォルダの絶対パスを 1 行で書き足す。すでにあれば足さない。ファイルがなければ作る。`/00-checkup all` は、この一覧にあるプロジェクトだけを点検する(ほかのフォルダの中身を読まないため)。

### 7. 報告する

作成したファイルの一覧、変更しなかった既存ファイル、次回点検日、最初に取りかかる作業を伝える。
